1. SSH на 127.0.0.1 vs правило фаервола
Подключиться снаружи не получится. Привязка сервиса (bind) главнее правила iptables.
Фаервол (iptables) лишь пропускает пакет до ядра ОС. Но ядро видит, что на внешнем IP (203.0.113.10) порт 22 никто не слушает (сервис ждет запросы только на 127.0.0.1), и отбрасывает соединение.
2. Чего не хватает namespace и роль MASQUERADE
Не хватает двух вещей: 1) шлюза по умолчанию (куда идти), 2) правила MASQUERADE.
Роль MASQUERADE: он подменяет внутренний приватный адрес источника (10.200.0.2) на внешний публичный адрес хоста (203.0.113.10), чтобы ответ из интернета мог вернуться обратно.
Если 10.200.0.2 уйдет «как есть»: роутеры провайдера его просто отбросят, так как приватные адреса в глобальном интернете не маршрутизируются.
3. Почему Docker обходит INPUT и ufw deny на порту 8080
Трафик попадает в цепочку FORWARD, а не в INPUT.
В самом начале (цепочка PREROUTING) Docker меняет адрес назначения пакета с внешнего IP на внутренний IP контейнера (DNAT). Увидев чужой IP, ядро понимает, что пакет идет «сквозь» хост (транзитом), и отправляет его в FORWARD. Команда ufw deny по умолчанию блокирует только цепочку INPUT (трафик, предназначенный самому хосту), поэтому на транзитный трафик в контейнер она не влияет.
4. Что сломается при прямом пробросе порта 8080 (вместо Nginx)
Опираясь на раздел 8, при прямом доступе (вариант а) станут неудобными или сломаются:
Безопасность (HTTPS): Придется настраивать и обновлять SSL-сертификаты внутри каждого отдельного контейнера. Nginx делает это централизованно (TLS-терминация), разгружая приложения.
Удобство адресов и маршрутизация: Пользователям придется писать в браузере адрес:8080. Nginx позволяет использовать стандартные порты 80/443 и направлять трафик в разные внутренние сервисы по имени домена, скрывая внутреннюю структуру сети.
